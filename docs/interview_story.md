# Interview Story: Ozon Delivery ML Pipeline

Файл-шпаргалка для рассказа проекта на собеседовании.

Проект: **локальный production-like ML pipeline для прогнозирования риска опозданий курьерских маршрутов**.

---

## 1. Главная идея проекта

Коротко:

> Я сделал end-to-end ML-проект, который имитирует промышленный контур доставки: данные генерируются, загружаются в разные хранилища, события проходят через Kafka, состояние маршрутов обновляется в Redis, признаки строятся на PySpark, модель обучается на route-level feature table, предсказания публикуются в PostgreSQL / Redis / ClickHouse, FastAPI отдаёт скоринг, Grafana показывает мониторинг, а Airflow оркестрирует весь процесс.

Ещё короче:

> Это локальная имитация production ML-системы для логистики: от сырых данных до API, мониторинга и Airflow.

---

## 2. Как рассказать проект за 30 секунд

> Я сделал локальный production-like проект по логистике доставки. Задача — заранее предсказывать, будет ли у курьерского маршрута хотя бы один опоздавший заказ. Я сгенерировал данные по складам, курьерам, маршрутам, заказам и событиям доставки. Данные загрузил в PostgreSQL и ClickHouse, поток событий имитировал через Kafka, состояние маршрутов и предсказания кэшировал в Redis. На PySpark построил route-level feature table, обучил baseline-модель классификации, опубликовал предсказания обратно в хранилища, сделал FastAPI для serving, Grafana dashboard для мониторинга и Airflow DAG для запуска всего pipeline.

Когда использовать:

- если HR просит коротко рассказать о pet-проекте;
- если интервьюер спрашивает: “А что это за проект?”;
- если нужно быстро обозначить масштаб.

## 3. Как рассказать проект за 2 минуты

> В проекте я решал задачу из домена курьерской доставки: заранее определить маршруты, у которых высокий риск опоздания.  
>  
> Бизнес-смысл такой: если заранее понимать, какие маршруты рискованные, можно перераспределить курьеров, уменьшить перегрузку маршрута, заранее отреагировать на плохую погоду или проблемную зону и снизить долю опозданий.  
>  
> Я построил локальный production-like контур. Сначала написал генератор синтетических данных: склады, курьеры, маршруты, заказы и delivery events. Справочные и транзакционные данные загрузил в PostgreSQL, события — в ClickHouse, а поток событий отправлял в Kafka. Отдельный consumer читал события из Kafka и обновлял Redis: state маршрута, state курьера, счётчики событий и последние события.  
>  
> Затем на PySpark я построил feature pipeline: собрал признаки на уровне маршрута — количество заказов, общий километраж, плановую длительность, загрузку курьера, погоду, час старта, день недели, тип транспорта, опыт курьера и историческую склонность к опозданиям. Target — `target_has_late_orders`, то есть был ли в маршруте хотя бы один опоздавший заказ.  
>  
> Модель обучал как бинарную классификацию. Использовал time-based split: train — более ранние даты, test — более поздние, чтобы не было утечки по времени. В качестве baseline сравнил Logistic Regression и Random Forest. Смотрел ROC-AUC, PR-AUC, LogLoss, Brier score, Precision@K и Recall@K.  
>  
> После обучения предсказания публикуются в PostgreSQL для аналитики, в Redis для быстрого доступа API и в ClickHouse как prediction events. Для serving сделал FastAPI, для мониторинга — Grafana dashboard, а весь pipeline завернул в Airflow DAG.

## 4. Как рассказать проект за 5 минут

### 4.1. Контекст

> Я хотел сделать проект, который не просто обучает модель в ноутбуке, а показывает полный путь ML-системы: данные, хранилища, обработка, модель, публикация предсказаний, API, мониторинг и оркестрация.

Задача похожа на реальные задачи логистики e-commerce / fresh-доставки:

- есть склады или dark stores;
- есть курьеры;
- есть маршруты;
- есть заказы;
- есть события доставки;
- нужно заранее понимать, какие маршруты с высокой вероятностью будут проблемными.

### 4.2. Бизнес-задача

> Цель — предсказать вероятность того, что в маршруте будет хотя бы один опоздавший заказ.

Target:

```text
target_has_late_orders
```

Интерпретация:

```text
1 — в маршруте был хотя бы один late order
0 — маршрут прошёл без late orders
```

Почему это полезно бизнесу:

- можно заранее увидеть проблемные маршруты;
- можно перераспределить курьеров;
- можно уменьшить перегрузку маршрута;
- можно предупредить оператора;
- можно контролировать SLA;
- можно строить мониторинг качества доставки.

### 4.3. Данные

Сущности:

- `stores` — склады / dark stores;
- `couriers` — курьеры;
- `routes` — маршруты;
- `orders` — заказы;
- `delivery_events` — события доставки.

Примеры событий:

- route started;
- courier arrived;
- order picked up;
- order delivered;
- delay event.

### 4.4. Хранилища

Использовал несколько хранилищ не просто так:

- `PostgreSQL` — для структурированных таблиц, предсказаний и витрин;
- `ClickHouse` — для событийной аналитики и prediction events;
- `Kafka` — для имитации потока событий доставки;
- `Redis` — для быстрого хранения актуального state и быстрых prediction lookup;
- `Parquet` — для feature table и промежуточного data layer.

Коротко:

> PostgreSQL — транзакционные и аналитические таблицы, ClickHouse — события, Kafka — поток, Redis — быстрый state/cache, PySpark — feature engineering.

### 4.5. Feature engineering

На PySpark строится таблица:

```text
one row = one route_id
```

Примеры признаков:

- `zone_id`;
- `day_of_week`;
- `start_hour`;
- `weather`;
- `vehicle_type`;
- `capacity_orders`;
- `base_speed_kmh`;
- `experience_days`;
- `historical_lateness_rate`;
- `num_orders`;
- `total_distance_km`;
- `planned_duration_min`;
- `capacity_utilization`;
- `total_weight_kg`;
- `total_volume_l`.

Важно:

> Я разделял признаки и target-колонки, чтобы не использовать будущую информацию и не получить data leakage.

### 4.6. Модель

Постановка:

```text
binary classification
```

Target:

```text
target_has_late_orders
```

Модели:

- `LogisticRegression` — простой интерпретируемый baseline;
- `RandomForestClassifier` — нелинейный baseline.

Почему не сразу сложная модель:

> Сначала я хотел сделать понятный baseline и проверить полный end-to-end контур. В реальной задаче следующим шагом я бы добавил CatBoost / LightGBM, подбор гиперпараметров и мониторинг дрейфа.

### 4.7. Валидация

Использовал:

```text
time-based split
```

То есть:

- train — старые даты;
- test — новые даты.

Почему:

> Для логистики и временных данных нельзя случайно перемешивать строки, потому что можно получить утечку из будущего. Time-based split ближе к реальному использованию модели: обучились на прошлом, предсказываем будущее.

### 4.8. Метрики

Смотрел:

- `ROC-AUC`;
- `PR-AUC`;
- `LogLoss`;
- `Brier score`;
- `Precision@K`;
- `Recall@K`;
- `Precision / Recall at threshold 0.5`.

Почему важны `Precision@K` и `Recall@K`:

> В операционной логистике часто важен не просто accuracy, а качество топа. Например, оператор может физически обработать только 20 самых рискованных маршрутов. Поэтому важно, сколько реальных проблем попало в top-K по скору модели.

### 4.9. Prediction publishing

После обучения предсказания публикуются в:

- `PostgreSQL → route_predictions`;
- `Redis → route:{route_id}:late_probability`;
- `Redis → route:{route_id}:prediction`;
- `ClickHouse → route_prediction_events`.

Зачем так:

- PostgreSQL — для витрин и SQL-аналитики;
- Redis — для быстрого ответа API;
- ClickHouse — для истории prediction events и аналитики по событиям.

### 4.10. API

FastAPI endpoints:

```http
GET /health
GET /routes/top-risky?limit=10
GET /routes/{route_id}/prediction
GET /metrics/summary
```

Логика:

> API сначала пытается взять prediction из Redis. Если в Redis нет значения, идёт в PostgreSQL. Так можно совместить быстрый cache lookup и fallback на надёжное хранилище.

### 4.11. Monitoring

В Grafana есть dashboard:

- количество заказов;
- lateness rate;
- P90 delay;
- top risky routes;
- risk buckets;
- precision / recall by day;
- Brier score;
- confusion matrix totals.

Зачем:

> Мне было важно показать не только обучение модели, но и мониторинг после публикации предсказаний: бизнес-метрики доставки и технические ML-метрики качества.

### 4.12. Orchestration

Весь процесс запускается через Airflow DAG:

```text
generate data
→ load PostgreSQL / ClickHouse
→ Kafka events
→ Redis update
→ PySpark features
→ train model
→ publish predictions
→ build dashboard tables
→ restart Grafana
→ check FastAPI
```

Зачем Airflow:

> Чтобы pipeline был воспроизводимым, задачам можно было задавать зависимости, видеть логи, перезапускать упавшие шаги и контролировать весь процесс из UI.

## 6. Вопросы, которые могут задать, и как отвечать

### Вопрос: Почему выбрал такую задачу?

Ответ:

> Я хотел взять задачу, близкую к реальной логистике маркетплейса: прогноз риска опоздания маршрута. Она хороша тем, что в ней есть и data engineering, и feature engineering, и ML, и monitoring, и serving. То есть можно показать не только модель, но и весь production-like контур вокруг неё.

---

### Вопрос: Почему target именно `target_has_late_orders`?

Ответ:

> Это простой и понятный бизнесовый target. Оператору важно знать, будет ли маршрут проблемным. Даже один опоздавший заказ может повлиять на SLA и клиентский опыт. Поэтому я начал с бинарной постановки: есть хотя бы один late order или нет. Дальше задачу можно расширить до регрессии количества опозданий, суммарного delay или quantile regression для оценки риска.

---

### Вопрос: Почему не предсказываешь точное время задержки?

Ответ:

> Можно было бы сделать регрессию на `target_total_delay_minutes` или `target_actual_duration_min`. Но для первого baseline я выбрал классификацию, потому что она ближе к операционному сценарию “какие маршруты нужно срочно проверить”. Это хорошо сочетается с Precision@K и Recall@K. Следующим шагом я бы добавил регрессионную модель или multi-task постановку.

---

### Вопрос: Почему PostgreSQL, ClickHouse, Kafka и Redis одновременно?

Ответ:

> Я специально развёл роли систем. PostgreSQL — для структурированных таблиц, предсказаний и витрин. ClickHouse — для событий и аналитики по большим логам. Kafka — для имитации потока delivery events. Redis — для быстрого доступа к текущему состоянию маршрута и prediction lookup в API. Это похоже на то, как системы разделяются в реальном production-контуре.

---

### Вопрос: Почему PySpark?

Ответ:

> Feature engineering по маршрутам хорошо ложится на Spark: нужно агрегировать заказы и события, делать join-ы, считать route-level признаки. Даже если локально данные маленькие, сама логика похожа на промышленную: raw events → distributed feature table → model training.

---

### Вопрос: Что такое `one row = one route_id`?

Ответ:

> Это гранулярность feature table. Каждая строка соответствует одному маршруту. В неё агрегируются признаки по заказам, курьеру, погоде, времени старта, событиям и плановым характеристикам маршрута. Target тоже считается на уровне маршрута: был ли хотя бы один late order.

---

### Вопрос: Как избегал data leakage?

Ответ:

> Я не использовал target-колонки и фактические будущие признаки как features. Также сделал time-based split: обучаюсь на более ранних датах, тестируюсь на более поздних. Это важнее случайного split, потому что в логистике данные имеют временную структуру.

---

### Вопрос: Почему time-based split лучше random split?

Ответ:

> Random split может перемешать прошлое и будущее. Тогда модель может косвенно увидеть паттерны из будущего периода, и качество будет завышено. Time-based split имитирует реальный production-сценарий: модель обучена на прошлом и применяется к будущему.

---

### Вопрос: Почему смотришь Precision@K и Recall@K?

Ответ:

> В логистике часто есть ограничение на число маршрутов, которые оператор может проверить. Например, можно обработать только top-20 самых рискованных маршрутов. Поэтому важно, насколько хороший top-K выдаёт модель. Precision@K показывает, какая доля top-K реально проблемная. Recall@K показывает, какую долю всех проблемных маршрутов мы поймали в этом top-K.

---

### Вопрос: Зачем Brier score?

Ответ:

> Brier score оценивает качество вероятностей. Для задачи риска важно не только правильно ранжировать маршруты, но и чтобы вероятность была калибрована. Если модель говорит 0.8, хочется, чтобы это действительно означало высокий риск, а не просто относительный score.

---

### Вопрос: Почему FastAPI берёт данные сначала из Redis?

Ответ:

> Redis нужен для быстрого lookup по `route_id`. Это удобно для online serving: API может быстро вернуть вероятность опоздания. PostgreSQL используется как fallback и более надёжное хранилище истории predictions.

---

### Вопрос: Что показывает Grafana?

Ответ:

> Grafana показывает бизнес-метрики доставки и ML-метрики. Например, количество заказов, lateness rate, P90 delay, топ рискованных маршрутов, распределение risk buckets, precision / recall по дням, Brier score и confusion matrix. Это помогает смотреть не только на качество модели offline, но и на поведение системы после публикации predictions.

---

### Вопрос: Что делает Airflow?

Ответ:

> Airflow оркестрирует весь pipeline: генерацию данных, загрузку в хранилища, Kafka, Redis, PySpark feature engineering, обучение модели, публикацию predictions, построение витрин, обновление Grafana и проверку FastAPI. Это делает процесс воспроизводимым и наблюдаемым.

---

### Вопрос: Что бы ты улучшил в следующей версии?

Ответ:

> Я бы добавил CatBoost или LightGBM, MLflow для tracking и model registry, real-time scoring consumer из Kafka, drift monitoring, тесты, CI, алерты Grafana и конфигурацию через `.env`. Также можно расширить постановку: предсказывать не только факт опоздания, но и ожидаемое время задержки или квантиль риска.

## 9. Как объяснить ML-часть одним блоком

> ML-часть начинается с route-level feature table: одна строка — один маршрут. Я агрегирую признаки по заказам, курьеру, маршруту, погоде и времени. Target — был ли хотя бы один опоздавший заказ. Использую time-based split, чтобы не было утечки по времени. В baseline сравниваю Logistic Regression и Random Forest. Метрики подбирал под задачу риска: ROC-AUC и PR-AUC для качества ранжирования, LogLoss и Brier score для вероятностей, Precision@K и Recall@K для операционного сценария top risky routes.

---

## 10. Как объяснить Data Engineering часть одним блоком

> Data Engineering часть состоит из генерации сырых данных, загрузки справочников и заказов в PostgreSQL, событий в ClickHouse, отправки delivery events в Kafka и обновления Redis consumer-ом. После этого PySpark читает raw parquet, агрегирует данные на уровне route_id и сохраняет feature table. Дальше модель обучается на этой таблице, а predictions публикуются в PostgreSQL, Redis и ClickHouse.

## 11. Как объяснить MLOps / production часть одним блоком

> Production-like часть проекта — это не только модель, но и всё вокруг неё: Docker Compose поднимает сервисы, Airflow управляет зависимостями задач, FastAPI отдаёт predictions, Redis ускоряет lookup, Grafana показывает мониторинг, а dashboard provisioning хранится как код. Это показывает, как модель может быть встроена в контур, а не просто обучена в ноутбуке.

> Проект локальный и на синтетических данных, поэтому я не делаю вид, что метрики отражают реальный бизнес. Главная цель — показать архитектуру, правильную постановку задачи, отсутствие leakage, pipeline, serving и monitoring. На реальных данных я бы отдельно занимался качеством данных, стабильностью признаков, feature store, drift monitoring, model registry и A/B или backtesting-проверками.

Ещё ограничения:

- синтетические данные;
- нет настоящего online scoring из Kafka;
- нет MLflow;
- нет CI;
- нет тестов;
- нет drift monitoring;
- нет алертов;
- модель baseline, не production champion.

Как правильно завершить:

> Но проект специально сделан как развиваемый skeleton: в него можно добавлять CatBoost, MLflow, drift monitoring, tests, CI и real-time scoring.

## 13. Что сказать, если спросят: “Это учебный проект?”

Хороший ответ:

> Да, это локальный учебно-прикладной проект, но я старался делать его не как ноутбук, а как production-like систему. То есть важна не только модель, а весь контур: данные, хранилища, streaming, feature engineering, prediction publishing, API, monitoring и orchestration. Именно поэтому там несколько инфраструктурных компонентов, Airflow, Grafana и FastAPI.

## 14. Что сказать, если спросят: “Какая здесь бизнес-метрика?”

Возможный ответ:

> Основная бизнес-метрика — снижение доли опоздавших заказов или снижение lateness rate. Дополнительно можно смотреть P90 delay, количество high-risk маршрутов, долю маршрутов с хотя бы одним late order, а также операционную метрику: сколько реальных проблемных маршрутов попадает в top-K, который может обработать диспетчер.

---

## 15. Что сказать, если спросят: “Как бы это работало в реальном production?”

Ответ:

> В реальном production данные приходили бы не из генератора, а из операционных систем: OMS, WMS, courier app, tracking events. События шли бы в Kafka, batch-слой строил бы регулярные фичи, online-слой мог бы обновлять state в Redis. Модель могла бы скорить маршруты по расписанию или по событию. Predictions попадали бы в API и dashboard для операторов. Airflow или другой orchestrator управлял бы batch pipeline, а Grafana / alerting следили бы за качеством данных, SLA и качеством модели.

---

## 16. Что сказать, если спросят: “Почему не сделал всё в одной базе?”

Ответ:

> Можно было бы упростить и хранить всё в PostgreSQL, но я хотел показать разделение ролей, близкое к промышленной архитектуре. В реальных системах события, transactional data, cache и analytical marts часто живут в разных инструментах. Поэтому ClickHouse отвечает за события, PostgreSQL — за структурированные таблицы и витрины, Redis — за быстрый доступ, Kafka — за поток.

---

## 17. Что сказать, если спросят: “Какой главный результат проекта?”

Ответ:

> Главный результат — воспроизводимый end-to-end ML pipeline. Одной кнопкой в Airflow можно пройти путь от генерации данных до обновлённого dashboard и работающего API с predictions. Это показывает, что модель встроена в контур использования, а не существует отдельно.

## 18. Мини-шпаргалка терминов

| Термин | Как объяснить |
| ------ | ------------- |
| `target_has_late_orders` | Был ли в маршруте хотя бы один опоздавший заказ |
| `route-level feature table` | Таблица, где одна строка соответствует одному маршруту |
| `time-based split` | Train на прошлом, test на будущем |
| `Precision@K` | Сколько из top-K рискованных маршрутов реально проблемные |
| `Recall@K` | Какую долю всех проблемных маршрутов поймали в top-K |
| `Brier score` | Насколько хорошо откалиброваны вероятности |
| `Redis cache` | Быстрое хранилище для state и predictions |
| `ClickHouse events` | История событий для аналитики |
| `Airflow DAG` | Граф задач pipeline с зависимостями |
| `Grafana dashboard` | Мониторинг бизнес- и ML-метрик |

## 19. Финальная версия рассказа

Можно выучить почти дословно:

> Я сделал локальный production-like ML pipeline для задачи прогнозирования риска опоздания курьерских маршрутов.  
>  
> Задача формулируется так: по признакам маршрута заранее предсказать вероятность того, что в нём будет хотя бы один опоздавший заказ. Это полезно для логистики, потому что оператор может заранее увидеть top risky routes и принять меры.  
>  
> Я сгенерировал данные по складам, курьерам, маршрутам, заказам и delivery events. Справочные данные и заказы загрузил в PostgreSQL, события — в ClickHouse, поток событий имитировал через Kafka, а Redis использовал для хранения актуального state маршрутов и prediction cache.  
>  
> На PySpark построил route-level feature table: одна строка — один маршрут. В признаки вошли погода, день недели, час старта, тип транспорта, опыт курьера, количество заказов, дистанция, плановая длительность, загрузка и агрегаты по заказам.  
>  
> Target — `target_has_late_orders`. Обучал бинарную классификацию, использовал time-based split, чтобы не было утечки по времени. В baseline сравнил Logistic Regression и Random Forest. Метрики: ROC-AUC, PR-AUC, LogLoss, Brier score, Precision@K и Recall@K.  
>  
> После обучения predictions публикуются в PostgreSQL, Redis и ClickHouse. FastAPI отдаёт предсказания по route_id и top risky routes, Grafana показывает бизнес-метрики и ML-мониторинг, а Airflow оркестрирует весь pipeline end-to-end.  
>  
> Главная идея проекта — показать не просто модель в ноутбуке, а полный контур: data engineering, feature engineering, ML, serving, monitoring и orchestration.
